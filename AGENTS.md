## Working with Codex (the primary coder)

This repo is driven by two agent systems, and **Codex is the primary coder**:
it plans, implements, tests, and reviews its own work end-to-end (full
review responsibility, not just execution). Claude Code runs the structured
pipeline (`/ship`, `/exterminate`, the subagents under `.claude/agents/`) as
the **review-gate / second opinion and budget-fallback** — use it when a
task genuinely needs the formal pipeline, or when Codex hits its rate limit.
The Raycast assistant acts as dispatcher and verifier: it hands out the
prompts and checks results, it does not implement.

Why Codex leads: on this account Codex delivers equal-or-better code quality
with far fewer tokens per task. Claude's `/ship` pipeline burns budget fast
through fixed over-serialized stages (planner/coder/tester/reviewer each
re-reading the repo), verbose per-agent context, repeated `.claude/pipeline/`
doc writing, and idle agent retries when rate-limited (429). Keep Claude
usage lean: single-pass prompts with all context inline, minimal subagents,
no retries, no exploratory phases.

Codex-specific rules (good practice for any agent):

Rules that apply to Codex specifically (and are good practice for any agent):

- **One working tree per task.** Never run a second agent (Codex or Claude)
  in the same dirty tree as another run. Check `git status --short` first;
  if it's dirty with files outside your task, stop and say so instead of
  starting. Use `git worktree add ../keepsake-<slug> -b <branch>` for any
  parallel work. (Two `ship` lanes once shared this tree and the reviewer
  saw a mixed diff — see MISTAKES.md.)
- **Commit by exact path, never `git add -A` / `git add .`.** Before every
  commit, run `git status --short` and confirm every staged file is one you
  actually edited. The pre-commit hook runs `pnpm preflight`; if it fails on
  a file you did not touch, that file belongs to another run — leave it.
- **MISTAKES.md is yours to write too.** The four triggers in the Docs
  section apply to every agent, including Codex. Log an entry in the same
  turn.
- **The pre-commit hook is the gate, not a suggestion.** If it fails, fix
  the cause (lint/format/typecheck) — never `--no-verify`.
- **Recovery, not heroics.** If you find a half-finished state from another
  run (uncommitted work, an open `.claude/pipeline/<slug>/`), read its
  `implementation-log.md` / `review.md` first and prefer committing /
  reporting over rewriting.

### Codex setup on this machine (verified 2026-08-30, CLI 0.151.0)

- **Interactive/profile use:** `cd /Users/rrosenzopf/keepsake-ui && codex -p keepsake`
  (profile file: `~/.codex/keepsake.config.toml`; inherits `approval_policy =
  "on-request"` and `sandbox_mode = "workspace-write"` from
  `~/.codex/config.toml`).
- **Non-interactive runs:** `codex exec --profile keepsake ...`. Note: `exec`
  defaults to `approval_policy = "never"`; pair it with `-s read-only` for
  checks/research, or rely on the profile's `workspace-write` sandbox for
  edits. Destructive or network actions still require the user.
- **Sub-agents (`spawn_agent`, multi-agent v2):** enabled globally via
  `features.multi_agent_v2 = true` in `~/.codex/config.toml`. Defaults set in
  `[orchestrator]` (both global config and the keepsake profile):
  `default_subagent_model = "gpt-5.6-luna"`,
  `default_subagent_reasoning_effort = "low"`,
  `max_concurrent_threads_per_session = 3`.
  - Luna = fast/affordable tier: scouts, test runs, narrow single-file edits.
  - Raise model/effort per spawn in the prompt for hard sub-tasks; do NOT
    raise the `[orchestrator]` defaults.
  - Concurrency cap of 3 is deliberate — fan-out burns the plan's rate
    limit fastest. Never ask Codex to spawn agents that all edit the same
    tree; sub-agents inherit this file's one-tree-per-task rule.
- **Model tiers available:** `gpt-5.6-sol` (frontier, default effort low),
  `gpt-5.6-terra` (balanced, default medium), `gpt-5.6-luna` (fast/cheap,
  default medium; supports efforts low..max, NOT "minimal" or "ultra").
  Valid effort values: `none`, `low`, `medium`, `high`, `xhigh`, `max`,
  `ultra` (sol/terra only).
- **Verification commands:** `codex --strict-config doctor` must show
  "config.toml parse ok"; `codex features list | grep multi_agent_v2` must
  show `true`. Session rollouts under `~/.codex/sessions/` record per-thread
  model + effort (check a sub-agent's `turn_context` if unsure what ran).

  Setup pitfalls learned while enabling multi-agent (2026-08-30), so they are
  never repeated:
  - Never put subagent keys under `[features.multi_agent_v2]` — it collides
    with the boolean feature key (`duplicate key` TOML error), and
    `enabled = true` inside the inline table fails with
    `data did not match any variant of untagged enum FeatureToml`. Subagent
    defaults belong ONLY in `[orchestrator]`; the feature is enabled ONLY as
    `multi_agent_v2 = true` inside `[features]`.
  - `gpt-5.6-luna` rejects `reasoning_effort = "minimal"` with an API 400.
    Luna supports `none|low|medium|high|xhigh|max`; `ultra` is sol/terra-only.
  - `codex exec` ignores `approval_policy` from profiles and runs with
    `never` — always pass `-s read-only` for check/research runs.
  - When verifying what a subagent actually ran, read the subagent's own
    rollout file's `turn_context` (model/effort/sandbox), not the parent's.
  - `codex doctor` accepts `--strict-config` only before the subcommand
    (`codex --strict-config doctor`), and `-p/--profile` is not a `doctor`
    flag — verify profiles by running a cheap `codex exec --profile keepsake`
    task instead.

### Codex self-review workflow (replaces the Claude gate for Codex work)

For every non-trivial task Codex runs the full loop itself:
plan → implement → run relevant tests + `pnpm preflight` → **self-review
pass** (`codex review`, or spawn a review subagent with a higher-effort
model — e.g. terra medium/high — that reviews the diff against the task's
success criteria) → fix findings → only then commit by exact path. Findings
worth remembering go into `MISTAKES.md` in the same turn. A human (or the
Raycast dispatcher) still verifies the final state before merge/deploy;
Codex self-review replaces the *pipeline* gate, not human judgment on the
design mission.


## What this is

Keepsake is a **UI fork** of [Karakeep](https://github.com/karakeep-app/karakeep)
(previously Hoarder), a self-hostable "read-it-later" bookmark manager. Same
bookmarking engine underneath — crawling, archiving, AI tagging and
summarisation, search, sync, the API, the mobile and browser clients — that's
all Karakeep's, unchanged. This fork does not add engine features. It replaces
the layer you look at: a denser list, a reading-focused detail view, a runtime
theme system, and a consistent visual language across the dashboard and
settings.

**Design mission, treat as fixed unless the user says otherwise:** no
thumbnails or image previews anywhere. Saved items are represented entirely by
their AI-generated title and AI summary, so the list reads like a briefing,
not a gallery.

## Design system — source of truth, read before touching any dashboard UI

- **`design/README.md`** — the full token spec: colour (default + alternate
  theme tones), typography scale, spacing, radius, and the elevation rule
  ("no shadows — surfaces separate by border and background-step only, keep
  it that way"). This is the design intent; treat its token tables as
  authoritative over any stray inline value elsewhere.
- **`apps/web/lib/dense/theme.ts`** — those tokens made real as
  runtime-switchable presets (accent / surface tone / reading emphasis). The
  file's own header comment states its values are transcribed from
  `design/README.md`, nothing invented. Keep that contract: a token change
  starts in `design/README.md`, then gets mirrored here — never the reverse.
- **`apps/web/app/dashboard/dense-theme.css`** — the CSS custom-property
  defaults / classes those presets override.
- **`design/presets/`** and the Figma export in `design/figma_keepsake_final/`
  — reference mockups for screens not yet built (mobile UI, search/filter).
  Check there before inventing a new layout from scratch.

## Project overview (upstream Karakeep — unchanged by this fork)

Karakeep is a monorepo managed with Turborepo. Tech stack:

- **Frontend:** Next.js (App Router), React, TypeScript, Tailwind CSS, shadcn/ui
- **Backend:** Hono, tRPC
- **Database:** Drizzle ORM (SQLite)
- **Tooling:** Oxfmt, oxlint, Vitest, pnpm workspace

### Applications (`apps/`)

- **`web`:** The main web application (Next.js) — this is where Keepsake's UI
  work happens. shadcn components live in `apps/web/components/ui`.
- **`browser-extension`:** Saves content to Karakeep from the browser.
- **`cli`:** Command-line interface for the service.
- **`landing`:** Landing page.
- **`mobile`:** Mobile app (Expo) — distinct from the `mobile/` subfolder
  inside `apps/web/components/dashboard/dense/`, which is this fork's own
  mobile *web* layout; the Expo app itself is untouched by the fork.
- **`mcp`:** Model Context Protocol server for talking to Karakeep.
- **`workers`:** Background processing (crawling, AI tagging/summarisation,
  search indexing) — its own process, started with `pnpm workers`.

### Packages (`packages/`)

- **`api`:** Hono app exposing the tRPC router as REST/OpenAPI — what the
  CLI, mobile app, browser extension and external API callers hit; wraps
  the same `appRouter` the web app calls in-process.
- **`db`:** Schema and migrations (Drizzle ORM).
- **`e2e_tests`:** End-to-end tests — a separate suite from the per-package
  Vitest units, needs a running server; check its own scripts before use.
- **`open-api`:** OpenAPI specs.
- **`sdk`:** SDK for the API.
- **`shared`** / **`shared-react`** / **`shared-server`:** Code shared across
  packages, by layer (plain utils / React hooks+components / server-only).
- **`trpc`:** tRPC router and procedures — most business logic lives here,
  under `routers/*.ts`, wired together in `routers/_app.ts`.

### How the pieces connect (web app)

- `packages/trpc/routers/_app.ts` is the single root router every surface
  goes through — the web app's server components, `packages/api`'s REST
  layer, the CLI, mobile and browser-extension clients all ultimately call
  into it.
- Inside `apps/web`, `server/api/trpc.ts` builds the tRPC context and
  `server/api/client.ts` exposes it as `api` for server components/route
  handlers to call directly (no HTTP round-trip); client components go
  through the usual React Query–backed tRPC client instead.
- `server/auth.ts` + `app/api/auth/[...nextauth]/route.tsx` is NextAuth;
  `app/api/[[...route]]/route.ts` mounts `packages/api`'s Hono app for
  everything that needs a real HTTP endpoint (webhooks, the public API,
  bookmark export).
- `app/dashboard/layout.tsx` is the authenticated shell: it wraps children
  with the dense theme/scale providers, the mobile shell, and reader
  settings, and gates on `getServerAuthSession()`. `app/dashboard/@modal`
  is a parallel route — `(.)preview` intercepts in-app navigation to a
  bookmark and renders it as a modal over the list instead of a full page
  load; `app/dashboard/preview` is the same view as a full page (deep
  links, refresh).

### Where the fork's own frontend work lives

Nearly all of Keepsake's UI-fork code — as opposed to inherited/lightly
patched Karakeep components elsewhere under `components/dashboard/` — is
under these two directories in `apps/web`:

- **`components/dashboard/dense/`** — the dense list/grid, detail read-out,
  sidebar (+ collapsed rail), theme and scale controllers
  (`DenseThemeController.tsx`, `DenseScaleController.tsx`,
  `ForceDenseTheme.tsx`), and `mobile/` — the fork's mobile layout.
- **`lib/dense/`** — the logic behind those components: `theme.ts` (the
  runtime preset system, see Design system above), plus small focused
  hook/util modules (`useDenseScale`, `useSidebarCollapsed`,
  `useRowNavigate`, `bookmarkDisplay`, `summary`, `format`), each paired
  with a co-located `*.test.ts`.

### Docs

- `docs/docs/03-configuration.md` — configuration options.
- `FORK_SYNC.md` — how this fork tracks and merges upstream Karakeep; read
  before resolving a conflict in a file both this fork and upstream touch
  (route pages under `dashboard/`, `EditorCard.tsx`, `ProfileOptions.tsx`,
  the AI inference workers, etc. — the file has the full list and why each
  tends to conflict).
- `MISTAKES.md` — log of things that broke or got corrected here. Check it
  before repeating an approach that looks familiar. Log mistakes in
  `MISTAKES.md` (what happened, root cause, prevention); when the same one
  recurs 4-5 times, promote it from there into a hard rule in this file.
  Log an entry in the same turn whenever:
  - a user correction happens (ordering, value, wording, scope — no matter
    how small);
  - a fix commit is needed because an earlier commit broke, mis-did, or
    left incomplete something (legitimate follow-on feature work doesn't
    count);
  - the same root cause recurs a second time (also flag it as a promotion
    candidate);
  - a guessed value or scope shipped as done without visual verification.

  The `mistakes-integrator` agent runs this same checklist after every
  `/ship` and `/exterminate` run to backfill anything missed.

## Common commands

- `pnpm typecheck` / `pnpm lint` / `pnpm lint:fix` / `pnpm format` /
  `pnpm format:fix` / `pnpm test` — run across every package via Turbo.
  `pnpm preflight` bundles typecheck+lint+format (read-only);
  `pnpm preflight:fix` runs the fixing variants.
- `pnpm db:generate --name description_of_schema_change` — after a schema
  change. `pnpm db:migrate` applies migrations; `pnpm db:studio` opens
  Drizzle Studio against the local SQLite db.
- `pnpm web` / `pnpm workers` — start a service (foreground, doesn't
  return); run both in separate terminals for local dev. Each needs its own
  `apps/web/.env` / `apps/workers/.env` with at least `DATA_DIR` and
  `NEXTAUTH_SECRET` (see root `README.md`).
- `start-dev.sh` — convenience script for the pieces `pnpm web`/`pnpm
  workers` don't start themselves: Meilisearch and headless Chrome via
  Docker (needed for search and crawling), plus `pnpm install` if
  `node_modules` is missing. Not needed for UI-only iteration.

### Running a single test

Each app/package has its own `vitest.config.ts` and a `test` script that is
just `vitest` (watch mode). To run one file or pattern once:

```bash
cd apps/web && pnpm exec vitest run lib/dense/theme.test.ts
# or, from repo root, without cd:
pnpm --filter @karakeep/web exec vitest run lib/dense/theme.test.ts
```

Plain `pnpm test` (root) fans out to every package's Vitest suite through
Turbo — fine for a final check, slow for iterating on one file.
